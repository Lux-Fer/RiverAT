# RiverAT 需求决策记录

**状态**：需求阶段收尾，待技术选型
**日期**：2026-10-29
**记录规则**：每条决策 = 结论 + 理由；未决事项进「待定」；影响架构但未验证的假设进「风险」。

---

## 1. 一句话定位

RiverAT（River + AT，AT = AutoTest）是面向**中大型公司测试团队**的产品组合自动化测试平台：把每个产品封装成插件，按产品树声明式编排测试，从版本创建一直跑到结果与证据产出。**平台不干预测试过程**，只保证"不漏测、可追溯、可分析"。

## 2. 背景与问题

- 测试工程师手里有多条产线，产品之间会组合成新产品（C = A + B），组合场景多、人工逐个测。
- 现状的痛点是**产品测试不完整**（漏测），不是结果字段缺失。
- 目标：从发版到测试结果输出全流程由 RiverAT 完成；插件规范对外公布，用户自行开发。

## 3. 决策

### 3.1 定位与边界

| ID | 结论 | 理由 |
|---|---|---|
| D1 | 双角色：测试工程师看"在跑什么 + 我的插件够不够用"；领导看"公司产品测试情况" | 两类人诉求不同；v1 先服务工程师，领导侧先给只读看板 |
| D2 | 平台 = 编排器 + 证据库 + 分析器，**不是用例管理系统** | 用例、断言、判定都归插件；平台只保证流程完整与留痕 |
| D3 | 平台不干预测试执行，只在权限内给建议 | 测试脚本是插件，装好后平台不再约束，只做记录与建议 |

### 3.2 产品组合与测试计划

| ID | 结论 | 理由 |
|---|---|---|
| D4 | 组合模型是**产品树**：新产品由旧产品组成（C = A + B），**不做全排列** | 组合数量是结构性的，不是指数级的；测试新产品只需把包含的旧产品加进去 |
| D5 | **版本锁死**：C 的每个版本只对应唯一的 A 版本 + B 版本 | 不锁版本，两次结果不可比、"上一轮过这轮挂"无法归因，知识库会喂进垃圾 |
| D6 | 变更传播**自动**：A 发版生成待办清单；C 的人发版后自动触发执行 | 人工决定一定漏；自动触发保证"组成变了一定跑" |
| D7 | 自动传播加三道闸：① 同 `(C 版本, A 版本)` 去重 ② 5 分钟合并窗口 ③ 自动任务默认最低优先级 + 每日机时预算 | 一次基础组件升级可能让几十个 C 同时进队列，会把机时打爆 |
| D8 | 测试计划 = **声明式 YAML**，借用 DSH/Cordis 的 row / group / insert / config / inject 模型 | 可进 Git、可 diff、可 review、可追溯；平台不做"该跑哪些"的智能推断 |

### 3.3 插件

| ID | 结论 | 理由 |
|---|---|---|
| D9 | 万物皆插件：测试工具、产品测试脚本都是插件；规范对外公布，用户自行开发 | 中大型公司的产品栈不可能统一，平台提供规则而不是提供实现 |
| D10 | 只借 DSH 的**契约层**（配置 schema、依赖注入、声明式组合、启停、隔离），不借运行时（同进程）与 UI slot | 契约层可一比一迁移；同进程运行时无法承载崩溃与依赖冲突 |
| D11 | 插件 = 一个产品/一项能力的适配器，**独立进程**运行，协议语言无关 | 客户产品栈有 C#/C++/硬件；进程边界同时解决崩溃隔离与依赖冲突 |
| D12 | 插件生命周期四段：`prepare / execute / collect / cleanup` | 与声明式计划的节点语义对齐，也便于超时与清理 |
| D50 | 插件包 = **tar.gz + `plugin.json`**（`entrypoints` 按目标系统声明）；运行时唯一参数是 `job.json` 路径 | tar 在 Linux/macOS/Windows 10+ 都有，不要求目标机装解压工具；参数走文件避免跨平台引号地狱 |
| D51 | 结果协议 = **退出码** + 可选 `plugin_result.json`（`status`/`reason`）+ 可选 `artifacts/`（顶层文件）；平台只采信与搬运 | 平台不裁判，但必须能拿到可复盘的事实；详见 `docs/plugin-contract.md` |

### 3.4 判定、完整性与证据

| ID | 结论 | 理由 |
|---|---|---|
| D13 | 执行路径由计划节点决定，**Agent 不进执行链** | 结果必须可复现、可审计；LLM 进执行路径会让同一计划两次跑出不同结果 |
| D14 | Agent 职责：稳定复现（**不改代码**）、根因分析、严重度判断、偶发/必现判定、用例合理性分析、资源建议 | 测试平台改被测代码 = 自己改自己测，独立性丧失；建议类能力不进入裁判链路 |
| D15 | **完整 = 计划内每个节点都有终态**（passed / failed / skipped / blocked / error），不是"全绿" | 要解决的是漏测，不是要都通过；一个环境问题导致整轮"没测"才是最痛的不完整 |
| D16 | 证据三件套：插件版本 + 包哈希、原始输出（stdout/stderr/截图/退出码）、环境快照（产品版本/依赖/机器/配置） | 平台不裁判，事故复盘必须能回答"谁判的、凭什么" |
| D17 | 失败后同环境自动重跑 2 次（共 3 次）：3/3 挂 = 必现；1~2/3 挂 = 偶发并记 flaky；换环境复跑由人触发 | 成本可控、口径可解释 |
| D18 | flaky 分 = `min(pass, fail) / total`，按 **(用例, 产品版本, 环境)** 分组；`>0.3` 判不可信、不阻塞发布 | 防止假红灯；分组是前提，否则版本回归会被误判成"不稳定" |

### 3.5 权限与调度

| ID | 结论 | 理由 |
|---|---|---|
| D19 | 优先级 = `base_priority`(1~5) + `override`（作用范围=本部门，有效期=24h） | "领导置顶"必须有时效和范围，否则一次误操作会长期污染队列 |
| D20 | 有效优先级 = `max(base, override)`，同级 FIFO；被抢占 = **暂停保进度** | 调度必须确定性，能向领导解释、能复现 |
| D21 | 角色初版：admin / engineer / viewer（领导 = viewer + 置顶权） | 待细化，见 Q5 |

### 3.6 执行环境

| ID | 结论 | 理由 |
|---|---|---|
| D22 | 测试机**不常驻、不主动连平台**；平台检查在线 → 推送执行 → 不在线通知负责人 | 中大型公司最难过的三关（常驻服务、入站端口、测试机出站）一次绕开 |
| D23 | 测试机 Windows + Linux 都有；Python / Docker / 出站网络**未确认** | 决定执行器形态（单文件二进制 vs 依赖 Python） |
| D24 | 插件隔离 v1：独立子进程 + 超时强杀 + 独立工作目录 + 声明式资源需求（端口/设备/license 排队） | 隔离是"敢让用户传插件"的前提；资源排队是组合测试的隐形工作量 |

### 3.7 知识库（RAG）

| ID | 结论 | 理由 |
|---|---|---|
| D25 | v1 只用平台自己的历史执行记录做失败归因；保留多源接入（公司资料、缺陷平台、测试文档、产品文档） | 零集成成本先验证归因质量；Jira 等要谈权限 |
| D26 | 知识模型三层：`source → doc → chunk`（pgvector） | 加来源只加连接器，不动表结构 |
| D27 | v2 加用例生成：产出**插件草稿**，人审后发布 | 不破坏"平台不干预"的定位 |

### 3.8 数据与验收

| ID | 结论 | 理由 |
|---|---|---|
| D28 | 核心 8 表：`product` / `product_version` / `version_component` / `plan` / `plan_node` / `plugin`(+version) / `run`(+run_step) / `evidence`；支撑表：`host`、`credential`、`notification`、`priority_override`、`audit_log`、`knowledge_source/doc/chunk` | 关系由 D4/D5/D8/D15 直接推出 |
| D29 | 领导页 5 个数字：① 放行结论分布（绿/黄/红）② 剔除 flaky 的通过率趋势 ③ 节点终态覆盖率 ④ 风险敞口（变更未回归 + 离线未执行）⑤ 端到端耗时 P50/P90 | 领导要的是"能不能发、有没有风险"，不是执行细节 |
| D30 | 现有技术栈（已定部分）：FastAPI + SQLAlchemy(async) + PostgreSQL + Redis + PyJWT/argon2 + Alembic + structlog；`frontend` / `plugin` / `rag` 未选型 | 见第 6 节 |
| D52 | 数据层测试跑**真 PostgreSQL + 真 Alembic 迁移**（临时库 `riverat_test`，用完即删），不用 SQLite 替代 | UUID / JSONB / 唯一约束都是 PG 语义；换库测试等于自己考自己 |
| D53 | `alembic.ini` 保持 **ASCII**；连接串留空，由 `migrations/env.py` 从 `.env` 读取，测试可覆盖 | configparser 按系统 locale 读文件，中文注释在 GBK 环境下会直接让 alembic 起不来 |
| D54 | v1 执行是**同步**的（`POST /runs` 等整轮跑完才返回）；队列化留到接 arq 时 | 先把"跑通 → 落库 → 页面可见"闭环做出来；接口形状不变，换实现不动调用方 |
| D55 | 计划由 `POST /plans` 创建，`definition` 接受 **JSON 或 YAML**；`depends_on` 做稳定拓扑排序，**依赖不存在/成环在创建时就返回 422**；运行时依赖未通过 → 下游 `blocked` | 错误要在"写计划"时就暴露，而不是跑到一半才发现；`blocked` 让"没测"和"测失败"在页面上可区分 |
| D56 | **产品树的 `parent_id`（组织归属）与版本组成 `version_component`（版本锁定）是两条独立的线**；组成在写时校验（子版本属于子产品、同子产品只锁一个、禁止自引用） | 组织上"属于哪条产品线"和"这一版到底用哪个子版本"是不同问题，混在一张表里会同时失去两者的语义 |
| D57 | 计划继承用 `includes: [{plan_id, prefix}]`：**只能引用当前版本已锁定的子版本的计划**；子计划节点 key 加前缀（默认子产品编码），依赖一起改写；展开后统一做 DAG 校验，创建时就返回 422 | 组合测试的本质是"父计划 = 子计划节点的并集 + 自己的集成节点"；把校验放在写入时，才不会跑到一半才发现引用错版本 |
| D58 | 测试机存在 `host` 表；密码用 **Fernet（密钥由 `SECRET_KEY` 派生）加密**入库，接口只回显非敏感字段；`run.host_id` 记录执行目标；远端工作目录 `/tmp/riverat-runs/<run_id>`，跑完删除 | 推送模型（D22）落地；凭据既不能明文入库，也不能通过 API 回显 |
| D59 | 计划**创建时冻结展开快照**（`plan.snapshot` + `snapshot_sha256`），执行只读快照；`run.plan_sha256` 记录本次用的是哪一版 | 回答 Q14：子计划之后被编辑，不会改变既有计划的行为，历史结果可复现 |
| D60 | v1 登录 = 本地账号（argon2）+ **服务端会话**：cookie 只带 token（HttpOnly / SameSite=Lax），会话数据在 Redis（测试用内存）；API 未登录 401，页面 303 跳 `/login`；首个管理员由 `ADMIN_PASSWORD` 引导 | 落地 D43；LDAP/SSO 只需换 Provider（D36/D40），`user.auth_source` 已留位 |
| D62 | 角色三级：`viewer`（只读）/ `engineer`（建产品、计划、跑测试）/ `admin`（再管测试机）；`role_at_least` 统一判定，写接口挂 `require_engineer` / `require_admin`；页面按角色隐藏表单，403 渲染友好页面 | 登录之后必须能区分"领导看"和"测试执行"；权限只定义一处，接口与页面表现一致 |
| D61 | 页面提供**表单操作**：建产品/版本/组成、建计划（YAML 文本框）、选测试机运行；表单与 API 走**同一套服务层校验**，错误以 422 页面回显 | 从"只能 curl"变成能自己用；校验只写一处，页面和接口不会各自漂移 |
| D63 | 用户管理：admin 通过 `GET/POST/PATCH /users` 建账号、改角色、停用；页面 `/users` 仅 admin 可见；**不能停用或降级自己** | 角色系统需要"发钥匙"的地方；自锁保护比事后改数据库便宜 |
| D64 | 部署 = 单机 **docker compose**（backend + postgres + redis）；镜像基于 `python:3.11-slim` + `requirements.txt`（由 `uv.lock` 导出，容器内不用 uv）；入口先 `alembic upgrade head` 再起 uvicorn；离线靠 `docker save/load` + `up --no-build` | 私有化交付必须有安装形态；ghcr 基础镜像在客户网络不可靠，Docker Hub 的 python 镜像更通用 |
| D65 | 执行走 **arq 队列**：`POST /runs` 只建 `queued` 记录并投递，worker 消费后执行；无 Redis 时回退**就地执行**（同一 `Dispatcher` 协议）；run 详情页在 queued/running 时自动刷新 | 同步执行会撞 HTTP 超时；队列把"点一下就跑"变成可轮询的状态机，且接口形状不变 |
| D66 | 领导页 `/dashboard`（viewer 及以上）：放行结论分布、通过率、**执行完整性**（步骤数 ≥ 计划节点数）、从未成功执行的产品版本数、端到端耗时 P50/P90；口径写在服务层并随字段返回 | D29 的 5 个数字落地；先给"能算且能解释"的口径，flaky 剔除等有足够数据再加 |
| D67 | 知识库 v1 只吃执行历史：失败/异常执行在收尾时写入 `knowledge_source/doc/chunk`（幂等）；检索用 **pg_trgm 相似度**（中文按字符三元组），不依赖 embedding 模型；以后接 Jira/文档只是新增 source 类型 | D25 的最小可用形态：离线可用、零外部依赖；等有真实归因需求再上向量 |
| D68 | 前端代码集中在仓库根 **`frontend/`**（`templates/` + `static/`）；后端通过 `app/web/templates.py` 单例引用并挂载 `/static`，`backend/app` 里不再放 HTML/CSS；Docker 构建上下文改为仓库根，镜像内 `/app/backend` 与 `/app/frontend` 平级 | 前端要有自己的目录；构建上下文跟着改，镜像内路径才和开发时一致 |
| D69 | D32 前端库落地：`frontend/static/vendor/` 内置 **HTMX 2.0.4** 与 **Chart.js 4.4.7**；run 详情改为片段轮询（`GET /runs/{id}/panel`，2s，结束后自动停），看板加近 14 天趋势折线图；删除整页 `meta refresh`；Alpine.js 仍无使用场景，暂不引入 | 局部刷新不打断已展开的日志；趋势图让数字可读；不 vendor 没人用的库 |
| D70 | 计划可编辑：`PATCH /plans/{id}`（engineer）+ 详情页编辑表单；改 `definition` → **revision + 1**、重新展开并冻结新快照，只改名不动 revision；`run.plan_revision` 记录执行时用的版本，旧 run 的 `plan_sha256` 不变；`definition` 解析改为**先 JSON 后 YAML**，解析错误统一 422 | 计划只能建不能改是语义缺口；用 revision 而不是覆盖，历史仍可复现（D59 的延伸） |
| D71 | 用户密码：创建与重置统一校验 **≥ 6 位**；admin 通过 `PATCH /users/{id} {password}` 或 `/users` 行内输入框重置他人密码，旧密码立即失效；v1 **不提供自助改密**；重置**不踢掉已登录会话**（会话按 token 存 Redis，未按用户索引） | 角色系统需要"换锁"能力；自助改密需要旧密码校验与额外页面，等真实需求再加；会话失效留到有审计需求时做 |
| D72 | 发布单 `release`：待发版本 + `target_date` + 状态（planned/released/cancelled）；**质量口径 = 建单之后该版本的所有执行**（不拿旧结果充数）；看板新增"未来 7 天待发"表；`/releases` 页面建单与标记已发布 | 让 D29 的"本周待发版本"落地；按建单时间切质量，语义清楚、不会把历史通过率算进来 |
| D73 | 发布详情页 `/releases/{id}`：四张质量卡（建单后执行/通过/失败·异常/最近一次）+ **属于这次发布的执行列表**（同版本且建单后创建，链到执行详情）+ 直接标记已发布 | 发布单从"列表一行数字"变成可下钻的验证记录；口径与 D72 完全一致 |
| D74 | 计划编辑**乐观锁**：`PATCH /plans/{id}` 接受 `expected_revision`（编辑表单隐藏字段自动带上），不一致返回 **409**；**改密码即下线**：会话存储新增 `revoke_user`（Redis 用 `user-sessions` 集合索引），重置密码后踢掉该用户全部会话，改自己密码则回登录页 | 两人同时改计划会静默互相覆盖；密码泄露后必须能强制下线 —— 这两条是多人可用的底线 |

## 7. 技术选型（2026-10-29 定：方案 A）

**结论**：采用方案 A —— 全 Python，不自研 agent 二进制。

**理由**：单人开发、Python 背景、离线私有化、需要在短期内跑通真机闭环。方案 A 不引入新语言，组件全部离线可装、无商业授权；WinRM 的域账号认证交给 Python 侧（`pywinrm` 支持 NTLM/Kerberos），而 Go 的 `masterzen/winrm` 只支持本地账号，这是当初排除 Go 执行器的主因之一。

| ID | 结论 | 理由 |
|---|---|---|
| D31 | 采用方案 A：FastAPI + paramiko/pywinrm 远端执行，无自研 agent | 单人 + 离线 + 尽快闭环；v2 再考虑 Go/Rust runner |
| D32 | 前端 = Jinja2 + HTMX + Alpine.js + Chart.js（vendored），不引入 Node 构建 | 不会 React/TS；页面以表单/表格/看板为主，HTMX 足够；离线可用 |
| D33 | 队列 = Redis + arq（异步原生） | 依赖面小、与 async SQLAlchemy 同类；停滞可平滑换 taskiq |
| D34 | 向量库 = pgvector，与业务同库 | 少一个组件，离线部署更简单 |
| D35 | 插件运行时 = 测试机解压便携 Python + 自带 wheels | 目标机不允许安装软件，但允许解压即用 |
| D36 | 认证 = 策略模式：`Local / LDAP / OIDC` 三个 Provider，统一 `authenticate() -> Identity`；`users.password_hash` 可空 | 密码来源不同，不能把三种逻辑塞进一个登录接口 |
| D37 | 产物先落本地卷 + 保留期清理，抽象出存储接口 | 20 GB/天单机可扛；后续换 MinIO / 共享盘不动业务代码 |
| D38 | 不做信创适配（数据库/OS），暂不投入 | 当前客户无硬性要求 |
| D39 | Rust 的学习位置：`riverat-pack`（插件打包/校验 CLI），不进关键路径 | 满足学习意愿，又不拿交付冒险 |
| D40 | 登录方式由 `AUTH_MODE` 配置：`local` / `ldap` / `oidc` / `mixed`；用户级 `auth_source` 决定走哪个 Provider | 迁移期需要"管理员本地账号 + 员工域账号"并存 |
| D41 | LDAP 走 LDAPS(636) 或 StartTLS；服务账号搜索 + 用户自身 bind；首登 JIT 建用户，**不存密码** | 明文 389 会把密码暴露在内网 |
| D42 | SSO 用 OIDC（`authlib`），校验 issuer/audience/nonce/PKCE；SAML 不做，除非客户硬性要求 | OIDC 是当前主流，SAML 成本高出一截 |
| D43 | Web 界面用服务端 session cookie（HttpOnly / SameSite=Lax），JWT 只给 API 与 agent | 模板 + HTMX 场景下把 JWT 塞前端很别扭，cookie 更自然也更安全 |
| D44 | 支持 LDAP/AD 组 → 角色映射（`group_dn → role`），未匹配则给最小权限 | 中大型公司上百人，手工分配角色不现实 |
| D45 | "本地模拟可信"由 **transport 契约测试**定义：同一套断言必须在 local 与真实 SSH 上同时通过 | 否则本地只是会撒谎的 mock；该套测试首次跑 SSH 就抓到了 env 传递缺陷 |
| D46 | 真机放行只认 spike 清单（远程执行/大文件/超时清理/中文路径/断线重连/无 Python 运行时） | 本地通过 ≠ 真机通过 |
| D47 | **超时必须真的结束执行**：本地杀进程树（`killpg` / `taskkill /T`），远端用 `timeout -k 5`；只"停止读取"不算数 | 实测本地 1.5s 超时被孙进程拖到 29.3s；SSH 超时后远端进程仍在跑 |
| D48 | **连接中断必须抛 `ConnectError`**，禁止用 `exit_code=-1` 表示 | 断连曾被伪装成"正常结束"，上游分不清事故与失败用例 |
| D49 | **输出必须封顶**：每路 8 MiB，超出截断并置 `truncated` | 全量缓冲进内存，一段失控日志就能打挂平台 |

**部署**：离线 docker compose（镜像 `save`/`load`），客户内网单机。
