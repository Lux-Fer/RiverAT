# RiverAT V0.1.2：人在环的失败恢复

> 目标不是把 RiverAT 变成无人值守 Agent，而是补上 V0.1.1 缺失的
> **执行结果回喂 → 有限重规划 → 人确认** 闭环。

## 1. V0.1.1 完成度审计

V0.1.1 的核心范围（模型配置、产品注册、工具安装/审核、对话生成任务草案、
人工确认、arq 执行、工作流与用例结果、权限与审计）已完成，验收结论为通过；
V0.1.1 自动化测试基线为 **201 passed / 4 skipped**，V0.1.2 收尾为
**211 passed / 4 skipped**。

V0.1.1 验收报告中标为“已知限制”的项目不是缺陷，但需要在后续版本处理：

| 项目 | 状态 | 处理 |
|---|---|---|
| 单机 Compose / 无 HTTPS / 无告警 | 已知限制 | V0.1.2 已补安全基线；实际域名 TLS 仍需部署时提供 |
| 工具无沙箱、仅本地执行 | 已知限制 | 留到运行时加固阶段 |
| CI 配置只存不发 | 已知限制 | 留到真实 CI 集成 |
| 工具工作目录/产物不回收 | 已知限制 | 留到数据生命周期 |
| v1.0 冻结 API 仍挂载 | 遗留 | 单独清理，不与本版混做 |

验收后已完成的补强：队列自愈与原子认领、产品归档/编辑、工具停用/启用、
生产 SECRET_KEY 守卫、数据库/Redis 端口收敛、备份/恢复脚本。V0.1.1 作为
“可交付的人确认工作流”已完整；V0.1.2 从这里向上走。

## 2. V0.1.2 范围

### 2.1 失败观察与修复草案

任务中某个步骤进入 `failed` / `error` 后（Agent 恢复开启时）：

1. 停止后续 pending 步骤，标为 `skipped`，写明“前置步骤失败，未执行”；
2. 汇总已执行步骤的 `status / exit_code / stderr / cases / error`；
3. 把观察结果和原需求、可用工具一起交给模型；
4. 模型最多提出 `AGENT_RECOVERY_MAX_STEPS`（默认 3）个工具调用；
5. 平台校验工具名和参数 schema；
6. 不直接执行，而是创建一个新的 `draft` 任务，带 `recovery_of` 和
   `replan_count`；
7. 原任务详情显示“Agent 修复建议”，人打开新草案、确认后才执行。

关闭 `AGENT_RECOVERY_ENABLED` 时保留旧策略：单步失败不中断后续步骤。

限制：

- 每条失败链最多 `AGENT_REPLAN_LIMIT`（默认 2）次；
- 模型不可用、无合法工具或参数不完整时，只在原任务记录 `no_plan` 原因；
- 修复草案仍走原有确认/审计/执行链路；
- 不自动放开新的副作用工具。

### 2.2 修复结算

修复任务成功后：

- 沿 `recovery_of` 链标记失败祖先的 `resolved_by_task_id / resolved_at`；
- **不覆盖**原来的 `failed` / `error` 状态；
- 原任务详情显示“已由后续修复任务解决”，可点回修复任务；
- 写 `task.resolved` 审计。

这样统计能区分“原始失败”和“已解决”，也不会篡改历史。

### 2.3 出站脱敏与截断

模型调用前统一处理：

- 递归替换 `password / token / secret / api_key / authorization / cookie` 等敏感键；
- 正则清洗 URL 内嵌密码、Bearer、键值对、JWT、常见供应商 token；
- 观察总长上限 8000 字符，`stderr / args / cases` 分段截断；
- 历史聊天同样脱敏后再送入模型。

这是最低限度的出站保护，不是完整 DLP；工具输出仍按不可信数据对待。

### 2.4 多轮上下文

助手规划时读取**同一用户**最近的对话消息（最多 6 条，单条截断 1200 字），
而不是只发当前一句。`list_messages` / `latest_draft` 按 `Task.created_by`
过滤，避免多人共用一个界面时把别人的会话带进模型。

### 2.5 终态先提交，再调用模型

任务终态和步骤结果先 `commit`，然后才进行修复规划：

- 模型慢/不可用不会让任务一直显示“运行中”；
- 不再在数据库事务里等最长 60 秒的模型请求；
- 修复草案写入失败时，任务本身的失败结果已经保留。

### 2.6 明确不做

- 不在执行中自动调用新工具；
- 不做工具沙箱、远程 runner；
- 不做真实 CI 回调；
- 不删除 v1.0 冻结 API。

## 3. 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `AGENT_RECOVERY_ENABLED` | `true` | 是否生成失败修复草案 |
| `AGENT_RECOVERY_MAX_STEPS` | `3` | 单次修复草案最多工具调用 |
| `AGENT_REPLAN_LIMIT` | `2` | 一条失败链最多重规划次数 |

## 4. 验收

- 失败任务产生新 draft，原任务可见入口；
- 修复草案步骤参数合法，未通过 schema 的调用不会进入草案；
- 模型无方案时原任务记录原因，不产生空任务；
- 达到重规划上限后不再调用模型；
- 修复成功后原失败任务显示“已由后续修复任务解决”，原状态保留；
- 敏感键、URL 密码、Bearer/JWT 等在出站 prompt 中被替换；
- 多步骤观察总长受限，不会无限撑大 prompt；
- Agent 恢复开启时，首个失败步骤后的 pending 步骤标为 skipped 且不再调用工具；
- 任务终态在模型调用前已提交，模型不可用不影响任务落库；
- 多轮上下文按用户隔离，且顺序稳定；
- 全量测试通过，V0.1.2 镜像可启动；
- 真模型冒烟：用失败观察触发一次修复规划，生成了 1 步修复 draft；
- 事务回滚验证，冒烟数据未写入生产库。

## 5. 与“完整 Agent”的距离

V0.1.2 仍是**人在环**：模型观察结果后提出下一步，但人保留批准权。
真正的自主闭环还需要：执行中逐步观察、风险分级授权、步骤级重试/恢复、
沙箱与轨迹评估。V0.1.2 先把“观察结果”接进控制流。
